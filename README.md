# Голосовой ассистент для задач и встреч

MVP голосового ассистента: пользователь отправляет текст или голосовое сообщение,
сервис распознаёт речь, разбирает запрос, сохраняет задачу, напоминание или встречу
и отвечает текстом и озвучкой.

Код разделён на бэкенд `src/TaskManager`, сервисы `src/stt` (Speech-to-Text),
`src/nlu` (Natural Language Understanding), `src/tts` (Text-to-Speech) и web-клиент
`src/web`. Инфраструктура и Docker Compose лежат в `deploy/`.

## Быстрый запуск

```bash
cp deploy/.env.example deploy/.env
# Windows: copy deploy\.env.example deploy\.env

# Заполнить LLM_API_KEY и EMBEDDING_API_KEY, если нужен полноценный NLU.
# Если поставить RULES_ONLY=true, NLU будет использовать правила вместо внешних моделей.

docker compose -f deploy/docker-compose.yml up -d --build
docker compose -f deploy/docker-compose.yml ps
```

Адреса сервисов:

- Веб-интерфейс: `http://localhost:8080`;
- TaskManager:
  - напрямую: `http://localhost:5000/api/v1/health`;
  - через web: `http://localhost:8080/api/v1/health`.

Нюансы запуска:

- первая сборка STT скачивает модель Whisper `base` (~150 МБ), поэтому занимает
  заметно больше времени;
- EF-миграции применяет one-shot `taskmanager-migrate` до старта API;
  в `docker compose ps -a` он должен быть в статусе `Exited (0)`;
- если порт `5432` занят локальным Postgres, укажите в `POSTGRES_PORT` любой
  свободный порт в `deploy/.env`;
- если порт `5000` занят, измените `TASKMANAGER_PORT`;
- web ходит в бэкенд по Docker-сети через `http://taskmanager:8080`;
- полный сброс данных: `docker compose down -v`.

## Архитектура

```text
                 HTTP + SSE                       HTTP
┌──────────┐                    ┌────────────────┐       ┌──────────────┐
│   web    │───────────────────►│  TaskManager   │──────►│  stt/nlu/tts │
└────┬─────┘                    └───────┬────────┘◄──────└──────────────┘
     │ presigned PUT/GET                │ SQL
     ▼                                  ▼
┌──────────┐                    ┌────────────────┐
│    S3    │                    │    Postgres    │
│audio/tts/│                    │turns, events,  │
└──────────┘                    │domain_commands │
                                └────────────────┘
```

`TaskManager` — модульный монолит с модулями `Turns` и `Events`.

`Turns` отвечает за весь путь запроса, сохранение контекста для черновика и уточнений,
генерацию ответов и делегирование задач другим сервисам.

`Events` отвечает за создание задач, напоминаний и встреч, нахождение конфликтов
между встречами и поиск по времени или значению.

`TaskManager` — единственный сервис с доступом к Postgres. `stt`, `nlu` и `tts`
не имеют доступа к БД и не общаются друг с другом. Аудио не проходит через бэкенд:
фронтенд загружает его в S3 по presigned URL, который выдаёт бэкенд, а затем бэкенд
передаёт ссылку на объект в STT. Ответ пользователю приходит по HTTP и SSE: текст
сразу, аудио позже (аудио также приходит в виде ссылки на S3).

Подробное описание: [docs/architecture.md](docs/architecture.md).

## Технологии

- **Backend:** C# / .NET 10, ASP.NET Core, EF Core, Npgsql, pgvector,
  Quartz.NET 4.x. Тесты — xUnit, NSubstitute, FluentAssertions, Testcontainers.
- **STT:** Python, FastAPI, faster-whisper.
- **NLU:** Python, FastAPI, OpenAI-совместимый LLM и embeddings.
- **TTS:** Python, FastAPI, edge-tts, S3.
- **Web:** React 19, TypeScript, Vite, nginx.
- **Инфраструктура:** PostgreSQL 17 + pgvector, RustFS (S3), Docker Compose.

## Компромиссы и решения, принятые в рамках сжатых сроков

- **Модульный монолит вместо микросервисов.** `Turns` и `Events` живут в одном
  процессе и одной транзакции. Это проще для MVP и сохраняет консистентность,
  но хуже для независимого масштабирования модулей.
- **Синхронные HTTP-вызовы и Quartz-задачи вместо брокера.** Меньше инфраструктуры
  и проще отладка, но ниже эластичность и устойчивость при нагрузке.
- **Один Postgres для доменных данных и Quartz.** Меньше компонентов и одна БД,
  но планировщик делит ресурсы с основным сервисом.
- **Presigned S3 URL вместо передачи аудио через бэкенд.** Бэкенд не проксирует
  бинарные данные и не тратит память на файлы; при этом нужно аккуратно
  настраивать хост и порт в подписи.
- **Фиксированная модель эмбеддингов.** `text-embedding-3-small`, размерность
  `1536`, HNSW-индекс. Это упрощает поиск и миграции, но привязывает систему
  к выбранной модели.
- **Шаблонные ответы и уточнения вместо полноценной истории диалога.** Поведение
  предсказуемо и тестируемо, но ответы хуже подстраиваются под пользователя.
- **One-shot `taskmanager-migrate` вместо auto-migrate при старте API.**
  Детерминированный порядок миграций и отсутствие гонок ценой ещё одного
  контейнера в compose.

### Текущие ограничения

- Нет аутентификации и мультипользовательского режима;
- Нет редактирования и удаления событий, а также смены их статусов;
- Качество NLU зависит от внешнего LLM и провайдера embeddings.

## Что можно было бы улучшить

- **Перейти на асинхронное общение вместо синхронных HTTP-вызовов и фоновых задач.**
  Брокер, outbox/inbox, независимые consumers, retries и DLQ. Это даст
  эластичность, масштабируемость и надёжность при отказах STT/NLU/TTS.
- **Использовать LLM для генерации ответа.** Сейчас ответы шаблонные; LLM позволит
  подстраиваться под стиль пользователя, а шаблоны останутся fallback.
- **Добавить полноценный контекст диалога.** Не только уточнения, но и историю
  последних ходов, разрешение местоимений и follow-up-запросы.
- **Добавить аутентификацию и мультипользовательский режим.** Изоляция данных,
  пользовательские настройки, часовые пояса и лимиты.
- **Добавить метрики, трассировку и алерты.** Наблюдаемость по ходам, фоновым
  задачам, внешним сервисам и ошибкам.
