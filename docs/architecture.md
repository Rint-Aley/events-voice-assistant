**Рамки:** MVP для показа жюри хакатона

Статусы решений: **FIXED** — договорено, изменение только через новую версию контракта;
**TBD** — решает владелец сервиса в своей спеке.

## 0. Как читать и как поддерживать документ

Этот файл — источник правды по **взаимодействию компонентов**: состав сервисов, потоки,
вызовы между сервисами, границы модулей. Здесь описано только то, что уже договорено.

Смежные документы:

- `docs/contracts/` — нормативные HTTP-контракты между компонентами: схемы
  `stt`/`nlu`/`tts`, общая ошибка, контракт web ↔ TaskManager;
- `docs/for_investigation.md` — всё, что ещё не решено: нефункциональные требования,
  отложенные темы, открытые вопросы. Это рабочая повестка, а не договорённость;
- `docs/task-manager.md` — устройство TaskManager: состояния, фоновые задачи, данные;
- `docs/<сервис>.md` — спеки остальных владельцев.

Здесь **не** описывается: какой провайдер STT/LLM/TTS выбран, какие промпты используются,
как устроены внутренние таблицы (это спека TaskManager), как выглядит UI.

Правила:

1. Контракты нормативны. Код, расходящийся со схемой, — баг, даже если «работает».
2. Изменение схемы = новый `schema_version` + правка схемы + запись в «История версий».
3. Владелец сервиса не меняет зону ответственности другого сервиса без обсуждения.
4. Спор о поведении решается этим документом, спор о формате — схемой.

## 1. Контекст и границы MVP

Пользователь формулирует задачу голосом или текстом в свободной форме; ассистент понимает
запрос, сохраняет или находит записи и отвечает текстом, озвучка догоняет отдельным шагом.

Обязательные сценарии:

1. Создание задачи/напоминания.
2. Создание встречи.
3. Выборка задач и встреч за период.
4. Поиск ранее созданных записей по смыслу.

Относительные даты («сегодня», «завтра», «послезавтра», «в пятницу», «через два часа»,
«на следующей неделе») обязательны.

Поиск по смыслу входит в MVP: вместе с планом действия NLU возвращает эмбеддинг текста,
TaskManager сохраняет его рядом с созданной записью и сравнивает с сохранёнными при поиске
(см. §4.4).

**Пользователь один.** Во всех таблицах и сообщениях есть `user_id`, но значение
константное (`DEMO_USER_ID`). Точка расширения до мультиюзера — middleware, подставляющий
`user_id` из токена; контракты и схема БД при этом не меняются.

## 3. Общая схема

```
                 HTTP + SSE                       HTTP
┌──────────┐                    ┌────────────────┐       ┌──────────────┐
│   web    │───────────────────►│  TaskManager   │──────►│  stt/nlu/tts │
└────┬─────┘                    └───────┬────────┘◄──────└──────────────┘
     │ presigned PUT/GET                │ SQL
     ▼                                  ▼
┌──────────┐                    ┌────────────────┐
│    S3    │                    │    Postgres    │
│audio/tts/│                    │turns, events,  │
└──────────┘                    │domain_commands │
                                └────────────────┘
```

| От | К | Транспорт | Что передаётся |
|---|---|---|---|
| `web` | `TaskManager` | HTTP | текст запроса или ключ загруженного аудио |
| `TaskManager` | `web` | SSE | смена состояния, текст ответа, ссылка на озвучку |
| `web` | S3 | presigned PUT | аудио записи |
| `web` | S3 | presigned GET | аудио ответа для проигрывания |
| `TaskManager` | S3 | presigned GET/PUT | ссылка для `stt`, ключ от `tts` |
| `TaskManager` | `stt` / `nlu` / `tts` | HTTP из фоновой задачи | задание; ответ приходит телом HTTP-ответа |
| `TaskManager` | Postgres | SQL | состояние ходов и доменные данные |

Ни один сервис, кроме TaskManager, не имеет доступа к базе и не общается с другими
сервисами напрямую.

## 4. Сквозные потоки

### 4.1 Голосовой запрос

| # | Откуда | Куда | Что |
|---|---|---|---|
| 1 | web | TaskManager | `POST /uploads` |
| 2 | TaskManager | web | `{upload_url, object_key}`, ссылка на 10 минут |
| 3 | web | S3 | `PUT` файла по presigned-ссылке |
| 4 | web | TaskManager | `POST /messages {object_key}` |
| 5 | TaskManager | web | `202 {turn_id}`, ход создан |
| 6 | web | TaskManager | `GET /turns/{id}/events` — SSE |
| 7 | TaskManager | stt | фоновый HTTP-вызов: ссылка на аудио, а не файл |
| 8 | stt | TaskManager | ответ: текст, уверенность, признак пустой записи |
| 9 | TaskManager | nlu | HTTP-вызов: текст + момент времени + контекст |
| 10 | nlu | TaskManager | ответ: план действия + эмбеддинг текста |
| 11 | TaskManager | домен | выполнение действия над `events` |
| 12 | TaskManager | web | SSE: текст ответа |
| 13 | TaskManager | tts | HTTP-вызов: текст ответа |
| 14 | tts | TaskManager | ответ: ключ готового аудио в S3 |
| 15 | TaskManager | web | SSE: ссылка на аудио |

**Текст ответа отдаётся сразу** (шаг 12), озвучка догоняет (шаг 15). Ход завершается по
тексту; отсутствие аудио — не ошибка.

### 4.2 Текстовый запрос

Тот же путь без шагов 1–3 и 7–8: `POST /messages {text}` → сразу вызов `nlu`.
Текстовые и голосовые запросы идут одним путём, чтобы не было двух расходящихся
реализаций.

### 4.3 Уточнение

`nlu` возвращает действие «уточнить» → ход переходит в ожидание ответа, черновик
сохраняется, пользователю уходит вопрос. Следующее сообщение несёт черновик в запросе к
`nlu` и мержится с новым планом.

Минимальное правило MVP: один уточняющий вопрос, черновик привязан к ходу и удаляется после
успешного создания записи или смены темы (`docs/task-manager.md` §7.5). Полные правила мержа
(TTL, число уточнений подряд) — LATER, `for_investigation.md`.

### 4.4 Эмбеддинги и поиск по смыслу

Главное правило: **описание и вектор живут парой.** Если есть что эмбеддить — описание записи
или поисковый запрос — `nlu` возвращает вектор вместе с планом. Если описания нет
(пользователь не сказал, о чём задача), `embedding` равен `null`, и запись просто не участвует
в семантическом поиске. TaskManager не решает «нужен ли вектор в этой ветке»: он сохраняет то,
что пришло, и требует вектор там, где есть описание.

```
TaskManager ── HTTP ──► nlu    (текст + момент времени + контекст)
TaskManager ◄─ HTTP ─── nlu    (план: действие + сущности; вектор, если есть что эмбеддить)
TaskManager ── домен:
      создание  → запись + её эмбеддинг сохраняются одной транзакцией
      поиск     → эмбеддинг запроса сравнивается с сохранёнными векторами
                  → ближайшие записи, отсортированные по близости
```

Требования к `nlu`:

- Вектор считается для всех действий, где есть текст: создание с описанием, поиск, уточнение
  по уже известному описанию. Для выборки за период и «не понял» эмбеддить нечего —
  `embedding: null`.
- Модель и размерность вектора — зона ответственности `nlu`. TaskManager о них не решает.
- Вектор детерминирован: тот же текст при той же модели даёт тот же вектор (важно при
  повторных вызовах `nlu`).

Требования к `TaskManager`:

- Вектор — **непрозрачные данные**: не пересчитывается, не нормализуется, не
  интерпретируется. Либо кладётся рядом с записью, либо передаётся в поиск как есть.
- Запись и её вектор (если он есть) сохраняются одной транзакцией: «создано, но не
  находится» невозможно.
- Описание без валидного вектора — ошибка контракта: запись с описанием обязана находиться
  поиском. Нет описания — нет и вектора; такая запись создаётся и ищется только по дате и
  типу.
- Сравнение — по косинусной близости; порог отсечения и число кандидатов — параметры домена,
  а не контракта.

Смена модели эмбеддингов — эксплуатационная задача (переиндексация существующих записей),
а не изменение flow. Поэтому здесь фиксируется только «вектор приходит от `nlu`», без
привязки к конкретной модели.

## 5. Взаимодействие TaskManager со stt, nlu и tts

TaskManager — единственный, кто общается с этими тремя сервисами. Между собой они не
связаны, в базу не ходят и о существовании друг друга не знают. Вызов — обычный
HTTP-запрос из фоновой задачи TaskManager: сервис получает задание в теле запроса и
отвечает результатом в теле ответа. Для пользователя это всё равно асинхронно — запрос
принимается сразу, результат приходит событиями.

| Направление | Запрос | Ответ |
|---|---|---|
| TaskManager ⇄ `stt` | ссылка на аудио в S3 + параметры распознавания | текст, уверенность, признак пустой записи |
| TaskManager ⇄ `nlu` | текст запроса + момент времени и таймзона + контекст | план действия, сущности, эмбеддинг текста |
| TaskManager ⇄ `tts` | текст ответа + голос + формат | ключ готового аудио в S3 + длительность |

### 5.1 Распознавание речи (`stt`)

**Особенность:** аудио в запросе не передаётся. Файл лежит в S3, в задании — только
ссылка с ограниченным временем жизни. Это снимает лимит размера сообщения и убирает
необходимость давать сервису доступ к бакету.

Что передаёт TaskManager: ссылку на объект, тип содержимого, язык, предельную длительность.

Что возвращает `stt`: распознанный текст, язык, длительность записи, уверенность и признак
«запись пустая».

Договорённости:

- пустая расшифровка — валидный результат, а не сбой: TaskManager сам решает, что сказать
  пользователю;
- язык фиксирован (русский), автодетект не требуется;
- длительность записи ограничена, ссылка живёт дольше, чем занимает обработка.

### 5.2 Понимание запроса (`nlu`)

Что TaskManager обязан передать:

- текст запроса;
- текущий момент с офсетом и таймзону — `nlu` не определяет «сегодня» самостоятельно;
- контекст: черновик незавершённого уточнения и последние записи (для «перенеси её»).

Что возвращает `nlu`:

- тип действия: создание задачи, создание встречи, выборка за период, поиск, уточнение,
  «не понял»;
- сущности: заголовок, абсолютное время с офсетом **и** исходную фразу даты, период,
  поисковый запрос, ссылку на объект, длительность;
- уверенность и список недостающих слотов;
- эмбеддинг текста (см. §4.4).

Договорённости:

- `nlu` не выполняет действий и не пишет в базу — только описывает намерение;
- при низкой уверенности возвращается уточнение, а не догадка;
- исходная фраза даты нужна, чтобы TaskManager мог перепроверить разбор при сомнении;
- даты считаются относительно переданного момента, а не системного времени сервиса.

### 5.3 Синтез речи (`tts`)

**Особенность:** аудио снова не передаётся в запросе. `tts` кладёт файл в S3 и возвращает
ключ объекта, длительность и признак попадания в кэш.

Договорённости:

- ключ объекта детерминирован по содержимому (хэш текста и голоса), поэтому повторный ответ
  не синтезируется заново, а перезапись идемпотентна;
- озвучка не блокирует ответ: текст уходит пользователю раньше, аудио — отдельным событием;
- слишком длинный текст не озвучивается целиком (предел задаётся в спеке сервиса).

### 5.4 Общие правила обмена

- Каждый сервис предоставляет один HTTP-эндпоинт, который принимает задание и возвращает
  результат. Точные пути и схемы — в `docs/contracts/`.
- Вызовы выполняются в фоновой задаче TaskManager и не держат пользовательское соединение:
  сначала `202`, затем события SSE.
- Таймауты, число ретраев и поведение при исчерпании попыток — §6.
- Блобы не передаются: либо текст, либо ссылка на S3.
- Сервисы не вызывают друг друга напрямую и не имеют доступа к базе. Единственный владелец
  данных — TaskManager.
- Вызовы одного хода идут последовательно: следующий шаг начинается только после успешного
  предыдущего.

## 6. Фоновая обработка: таймауты, ретраи, идемпотентность

### 6.1 Модель исполнения

TaskManager принимает запрос, создаёт ход в Postgres и сразу отвечает `202`. Дальше ход
двигают фоновые задачи. Их состояние и попытки держит планировщик в своём сторе в Postgres —
своей таблицы задач TaskManager не заводит.

Ключ задачи детерминирован: `stt:{turn_id}`, `nlu:{turn_id}`, `tts:{answer_id}`. На ключ
приходится не больше одной задачи, поэтому повторная постановка безопасна, а разрыв между
коммитом и постановкой закрывает `reconciler` (§6.2).

Обработчик выполняет шаг и записывает результат: данные и новое состояние хода — одна
транзакция. Последовательность шагов — та же, что в §4:

1. `stt` — голосовой вход, сохранить текст;
2. `nlu` — сохранить план и намерения записи;
3. `domain` — применить намерения, отдать текст ответа по SSE;
4. `tts` — отдать ссылку на аудио.

Записи домена не создаются в обработчике `nlu` напрямую: он кладёт `domain_commands` в той же
транзакции, что и состояние, а применяет их отдельный тик — одной транзакцией на ход. Это
заменяет outbox: намерение не может потеряться, потому что уже лежит в БД.

### 6.2 Падение процесса

- Задачи и намерения не теряются: они в Postgres. Незавершённую задачу планировщик поднимает
  после старта (`RequestRecovery`), обработчик идемпотентен.
- Счётчик попыток переживает рестарты: задача, которая стабильно роняет процесс, после
  `max_attempts` становится `failed`, ход — в терминальное состояние с ошибкой.
- Повторный запуск шага безопасен: переход состояния — CAS, а запись в домен и смена состояния
  — одна транзакция.
- `reconciler` раз в 10 с закрывает просроченные ходы в `EXPIRED`, добивает потерянные задачи
  и помечает зависшую озвучку как `failed`.
- Ограничение MVP: одна реплика. `FOR UPDATE SKIP LOCKED` при выборке `domain_commands`
  используется сразу — он ничего не стоит и снимает вопрос при второй реплике.

### 6.3 Таймауты и ретраи

| Шаг | Таймаут | Попыток | Если попытки исчерпаны |
|---|---|---|---|
| `stt` | 30 с | 3 | ход завершается ошибкой распознавания |
| `nlu` | 20 с | 3 | ход завершается ошибкой разбора |
| `tts` | 20 с | 3 | текстовый ответ остаётся, аудио не приходит |
| применение команд | локально | 3 | ход завершается ошибкой применения |

- Попытки и паузы между ними ведёт планировщик; счётчик не сбрасывается при рестарте
  процесса.
- Ретраи только на сетевые ошибки, таймауты и 5xx. Ответ 4xx не повторяется: это ошибка
  запроса, а не сбой.
- Пауза между попытками — перепланирование с задержкой (экспоненциальная, с небольшим
  потолком), а не `sleep` в обработчике: процесс не блокируется.
- Повторный вызов `tts` идемпотентен по построению: ключ объекта — хэш текста.
- Общий дедлайн хода (90 с) ограничивает сумму всех попыток.

### 6.4 Идемпотентность

- Каждый вызов несёт идентификатор хода: сервис может использовать его в логах и для
  собственного кэша, но состояние хода ему неизвестно и не нужно.
- Сервисы stateless: повторный вызов — это повторная работа, а не второй побочный эффект.
- Домен изменяется ровно один раз на ход: запись и смена состояния — в одной транзакции,
  поэтому повтор шага после падения не создаёт вторую запись.

### 6.5 Чем платим за простоту

- Нет буфера между TaskManager и сервисами: недоступность сервиса сразу видна пользователю
  как ошибка после трёх попыток (с брокером сообщение ждало бы в очереди).
- Нет горизонтального масштабирования обработки: всё в одном процессе.
- Нет воспроизведения истории вызовов (replay), которое даёт журнал брокера.
- Порядок шагов держится на состоянии хода и очереди задач, а не на порядке сообщений в
  брокере; при нескольких репликах нужна аккуратность с захватом задач.

Переход на брокер и outbox вместе с сохранёнными деталями — в `for_investigation.md`.

## 7. Данные

Владелец — модуль `domain` (для `events`) и `fsm` (для `turns`, `drafts`, `answers`,
`domain_commands`). Одна база Postgres, расширение `pgvector`.

| Таблица | Владелец | Назначение |
|---|---|---|
| `turns` | fsm | ход диалога: состояние, план, текст, дедлайн |
| `domain_commands` | fsm | намерения записи из `nlu`; применяются тиком |
| `events` | domain | задачи, напоминания, встречи |
| `drafts` | fsm | недособранный запрос, привязан к ходу |
| `answers` | fsm | ответ хода и ссылка на озвучку |
| `answer_events` | fsm | связь ответа с созданными или найденными записями |

Таблицы сессий нет: сессия одна и задана константой в конфиге. Таблицы задач тоже нет — её
держит планировщик в своём сторе.

Минимальная форма `events` (полная схема — в `docs/task-manager.md`):

```
id, user_id, kind(task|reminder|meeting), description, embedding, embedding_model,
starts_on, starts_at (timetz), duration (interval), status, source_turn_id,
created_at, updated_at
```

`kind` объединяет типы в одну таблицу: выборка за период и поиск работают одинаково,
различия — в доменных методах. `description` и `embedding` хранятся парой: без описания нет
вектора, и такая запись не находится семантическим поиском. Вектор — `pgvector`; при поиске
домен сравнивает с ним вектор, полученный от `nlu` (§4.4).

## 8. Граница модулей внутри TaskManager

Один процесс, модули `http`, `fsm`, `domain`, `jobs`, `sse`; зависимости строго в одну
сторону: `http → fsm → domain`, `fsm → jobs`, `fsm → sse`.

```python
class TodoDomain(Protocol):
    def create(self, cmd: CreateEvent) -> Event: ...
    def list_period(self, q: PeriodQuery) -> list[Event]: ...
    def search(self, q: SearchQuery) -> list[Event]: ...
    def update(self, cmd: UpdateEvent) -> Event: ...
    def complete(self, event_id: UUID) -> Event: ...
    def delete(self, event_id: UUID) -> None: ...
```

Правила:

- `domain` не импортирует `fsm`, не знает про HTTP, SSE и фоновые задачи, ничего не
  публикует.
- `fsm` не пишет в `events` напрямую и не строит SQL.
- Транспорт (HTTP/SSE) — тонкий слой над `fsm`.
- Домен возвращает типизированные ошибки (`EventNotFound`, `InvalidPeriod`,
  `TitleRequired`, `TimeInPast`), `fsm` решает, как их превратить в ответ пользователю.

Детали состояний, переходов, задач и схемы данных — в `docs/task-manager.md`.
