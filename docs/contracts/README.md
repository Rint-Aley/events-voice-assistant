# Контракты

Версия набора: 2 (HTTP). Владелец: бэкенд. Основано на `docs/architecture.md` v0.8 и
`docs/task-manager.md`.

Здесь лежат **действующие** контракты: HTTP-обмен между компонентами системы. Схемы
брокера (`envelope.json`, `*.job.json`, `*.result.json`, `dlq.json`) выведены из работы и
перенесены в `archive/` — они понадобятся только при переходе на брокер
(`docs/for_investigation.md` §4).

## Кто с кем говорит

| Направление | Транспорт | Контракт |
|---|---|---|
| web → TaskManager | HTTP + SSE | `http-api.md` |
| TaskManager → stt | HTTP | `stt.request.json`, `stt.response.json` |
| TaskManager → nlu | HTTP | `nlu.request.json`, `nlu.response.json` |
| TaskManager → tts | HTTP | `tts.request.json`, `tts.response.json` |
| stt / nlu / tts → TaskManager (ошибка) | HTTP | `error.json` |

Сервисы не общаются между собой и не имеют доступа к БД. Единственный, кто их вызывает, —
TaskManager. В MVP сервисы не публикуются наружу: только внутри compose-сети, без
авторизации.

## Состав

| Файл | Что описывает | Эндпоинт |
|---|---|---|
| `stt.request.json` | запрос на распознавание | `POST /v1/transcribe` |
| `stt.response.json` | результат распознавания | `200` |
| `nlu.request.json` | запрос на разбор текста | `POST /v1/interpret` |
| `nlu.response.json` | план действия, сущности, эмбеддинг | `200` |
| `tts.request.json` | запрос на синтез | `POST /v1/synthesize` |
| `tts.response.json` | ключ готового аудио | `200` |
| `error.json` | тело любого не-2xx ответа | — |
| `http-api.md` | HTTP + SSE для web | `/api/v1/...` |

## Общие правила

1. **Только JSON.** `Content-Type: application/json; charset=utf-8`, тело ≤ 100 КБ.
   Никаких блобов: аудио на вход — presigned GET, аудио на выход — ключ объекта в S3.
2. **Один вызов — один ответ.** Без callback, webhook и long-polling. Пользовательское
   соединение вызов не держит: он идёт из обработчика фоновой задачи.
3. **Версия в пути.** Ломающее изменение — новый префикс `/v2`, старый живёт до миграции.
   В MVP сервисы релизятся вместе, поэтому добавление поля делается одним релизом без
   смены префикса.
4. **`additionalProperties: false` везде.** Лишнее поле — ошибка контракта, а не «клиент
   что-то добавил». Это ловит расхождение схемы и кода до продакшена.
5. **Идемпотентность по ключу.** `turn_id` для `stt`/`nlu`, `answer_id` для `tts`.
   Сервисы stateless: повтор с тем же ключом даёт тот же результат (`tts` отвечает
   `cached: true`), дубля в S3 не появляется.
6. **Время.** Моменты — RFC 3339 с offset (`2026-10-23T14:05:00+03:00`); даты —
   `YYYY-MM-DD`; локальное время суток — `HH:MM` плюс `timezone` в запросе. Длительности
   на границе TaskManager↔сервис — в минутах (`duration_minutes`) или миллисекундах
   (`duration_ms`); внутри БД — `interval`.
7. **Таймзоны.** MVP считает, что пользователь в одной зоне (`TIMEZONE` в конфиге).
   Смещение в `timetz` берётся на дату события; переходы на летнее время не учитываются.
8. **Эмбеддинг.** `nlu` возвращает его вместе с планом. `description` и `embedding` —
   пара: нет описания — `embedding: null`. `dim` обязан совпадать с длиной `values`;
   это проверяет TaskManager, схема такую зависимость выразить не может.
9. **Порядок.** Для одного `turn_id` TaskManager не делает два параллельных вызова.
   Повторная доставка результата обрабатывается по CAS на состоянии хода.

## Таймауты и ретраи

Ретраи делает TaskManager, сервисы о повторах не знают.

| Вызов | Таймаут | Попыток | Что при исчерпании |
|---|---|---|---|
| `POST /v1/transcribe` | 30 с | 3 | ход `FAILED`, `STT_FAILED` |
| `POST /v1/interpret` | 20 с | 3 | ход `FAILED`, `NLU_FAILED` |
| `POST /v1/synthesize` | 20 с | 3 | `audio_status = failed`, текст ответа остаётся |

Повторяются таймауты, сетевые ошибки и `5xx`. `4xx` не повторяется: это ошибка запроса.

## Коды ответов

| Код | Когда | `retryable` |
|---|---|---|
| `200` | успех | — |
| `400` | тело не соответствует схеме | `false` |
| `422` | тело валидно, но запрос невыполним: `AUDIO_TOO_LONG`, `EMPTY_TEXT`, `UNSUPPORTED_FORMAT` | `false` |
| `503` | провайдер распознавания/модели/синтеза недоступен | `true` |
| `500` | внутренняя ошибка сервиса | `true` |

Тело ошибки — всегда `error.json`. `retryable` дублирует решение по коду, чтобы клиент не
разбирал статусы вручную; при расхождении приоритет у `retryable: false`.

## Совместимость

- Добавление необязательного поля в **ответ** — безопасно, потребитель его игнорирует не
  будет (схема закрыта), поэтому обе стороны обновляются одним релизом.
- Новое значение `action` в `nlu.response` — ломающее: TaskManager разбирает план
  исчерпывающе. Добавляется вместе с обработчиком, в одном релизе.
- Удаление и переименование полей, смена типа, новые обязательные поля — ломающее
  изменение: `/v2`.
- `schema_version` в телах HTTP не передаётся: версия живёт в пути.

## Как проверить

Самопроверка набора: схемы парсятся, позитивные примеры проходят, негативные — отбиваются.
Код возврата 1 при любой ошибке, годится для CI.

```bash
pip install jsonschema referencing
python docs/contracts/validate.py
```

Проверить свой документ против конкретной схемы:

```bash
pip install check-jsonschema
check-jsonschema --schemafile docs/contracts/nlu.response.json response.json
```

Архивные схемы проверяются отдельно: `python docs/contracts/archive/validate.py`.

## Чей контракт

| Контракт | Владелец схемы | Кто обязан обновиться |
|---|---|---|
| `stt.*` | владелец `stt` | TaskManager |
| `nlu.*` | владелец `nlu` | TaskManager |
| `tts.*` | владелец `tts` | TaskManager |
| `error.json` | TaskManager (общая форма) | все сервисы |
| `http-api.md` | TaskManager | web |

Владелец схемы принимает PR на изменение; потребитель обновляется в том же релизе.
Расхождение кода и схемы — баг, даже если «работает».
