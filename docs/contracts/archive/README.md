# Архив контрактов: обмен через брокер

> **Не используется.** Каталог — исторический. Схемы `*.job.json` / `*.result.json`,
> `envelope.json` и `dlq.json` описывают обмен через брокер, которого в MVP нет.
> Актуальные контракты — в `docs/contracts/` (HTTP между компонентами) и
> `docs/contracts/http-api.md` (web ↔ TaskManager).
>
> Сохранено как целевое состояние для перехода на брокер: `docs/for_investigation.md` §4.
> Скрипт `validate.py` рядом проверяет именно эти архивные схемы.

# Контракты (версия 1)

Нормативная часть архитектуры. Всё, что летит в брокере, описано здесь.
Изменять схемы можно только вместе с повышением `schema_version` и записью в
`docs/architecture.md` → «История версий».

## Состав

| Файл | Что описывает | Топик / канал |
|---|---|---|
| `envelope.json` | общий конверт любого сообщения | все топики |
| `stt.job.json` | запрос на распознавание | `stt.jobs.v1` |
| `stt.result.json` | результат распознавания | `stt.results.v1` |
| `nlu.job.json` | запрос на разбор текста | `nlu.jobs.v1` |
| `nlu.result.json` | план действий | `nlu.results.v1` |
| `tts.job.json` | запрос на синтез | `tts.jobs.v1` |
| `tts.result.json` | результат синтеза | `tts.results.v1` |
| `dlq.json` | сообщение в DLQ | `<сервис>.dlq.v1` |
| `validate.py` | самопроверка архива | — |

## Обязательные правила

1. **Конверт один для всех.** Схемы job/result — это `envelope.json` + жёстко заданный
   `job_type` и `payload` (`allOf`).
2. **Ключ партиции — `session_id`.** Не `turn_id`: иначе два сообщения одной сессии могут
   обогнать друг друга, и уточняющий диалог сломается.
3. **`message_id` не меняется при ретрае**, меняется только `attempt` (максимум 3).
4. **Никаких блобов.** Аудио — только ссылкой (`object_key` + presigned URL). Сообщение
   < 100 КБ.
5. **Консьюмер валидирует схему до обработки.** Невалидное сообщение — сразу в DLQ с
   `error.code = SCHEMA_INVALID`, без ретраев.
6. **Неизвестный мажор `schema_version`** — в DLQ, а не «попробуем распарсить».
7. **Дубли допустимы.** Любой консьюмер обязан корректно обработать повторную доставку.

## Совместимость

- Добавление необязательного поля — минорное изменение, версия контракта не меняется,
  но факт фиксируется в истории.
- Удаление/переименование поля, смена типа, новые значения в `enum`, новый обязательный
  слот — мажорное изменение: новый `schema_version` и новые топики (`*.vN`), старые живут
  до миграции.
- `payload` всегда `additionalProperties: false`: лишнее поле — ошибка контракта, а не
  «продюсер что-то добавил».

## Как проверить

Самопроверка архива (позитивные и негативные примеры, код возврата для CI):

```bash
pip install jsonschema referencing
python docs/contracts/archive/validate.py
```

Валидация своего документа против конкретной схемы:

```bash
pip install check-jsonschema
check-jsonschema --schemafile docs/contracts/archive/stt.job.json job.json
```

## Чей контракт

| Топик | Владелец схемы | Владелец топика (партиции, retention) |
|---|---|---|
| `stt.*` | владелец `stt` | `stt` |
| `nlu.*` | владелец `nlu` | `nlu` |
| `tts.*` | владелец `tts` | `tts` |
| `*.dlq.v1` | соответствующий сервис | соответствующий сервис |

Владелец схемы принимает PR на её изменение; потребители обязаны обновиться в том же
релизе.
