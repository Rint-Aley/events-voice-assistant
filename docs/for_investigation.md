## 4. Переход на брокер и outbox (после MVP)

Сохранённая схема асинхронного взаимодействия. Нужна, если после MVP понадобится буфер
между сервисами, независимое масштабирование обработки и воспроизводимость истории.

Текущее состояние (MVP): TaskManager вызывает сервисы HTTP-запросами из фоновой задачи.
Задачи и попытки держит планировщик в своём сторе, намерения записи — таблица
`domain_commands`; незавершённую задачу планировщик поднимает после рестарта
(`RequestRecovery`). Ниже — целевая схема, к которой имеет смысл вернуться.

### 4.1 Обмен сообщениями

- Все сообщения в общем конверте: версия схемы, идентификатор сообщения, тип задания,
  идентификаторы хода, сессии и пользователя, номер попытки, полезная нагрузка.
- Топики: `<сервис>.jobs.v1`, `<сервис>.results.v1`, `<сервис>.dlq.v1`.
- Ключ партиции — **сессия**, чтобы сообщения одного диалога не обгоняли друг друга.
- Блобы не передаются: ссылка на S3 или текст. Сообщение < 100 КБ.
- Каждый сервис — владелец своих топиков: схема, партиции, retention.

### 4.2 Outbox в TaskManager

| Место | Нужен ли | Почему |
|---|---|---|
| TaskManager → публикация задания | **outbox** | запись хода и отправка сообщения должны быть атомарны |
| TaskManager ← приём результата | inbox не нужен | CAS-переход отбрасывает дубли |
| `stt` / `nlu` / `tts` | inbox не нужен | своего хранилища нет; дубль результата безвреден |

Цикл:

1. Транзакция: обновить состояние хода + вставить строку в `outbox`.
2. Relay-цикл читает `outbox` через `FOR UPDATE SKIP LOCKED`, публикует, ставит `sent_at`.
3. Падение между публикацией и отметкой даёт дубль — он безопасен.
4. Relay — фоновая задача внутри TaskManager, не отдельный сервис. Debezium не нужен.

### 4.3 At-least-once в воркерах

Ключевое: **at-least-once не требует ни outbox, ни транзакций.** Outbox решает атомарность
«база + публикация», а у воркеров базы нет. Их side effect — сама публикация результата.

| Режим | Как | Следствие |
|---|---|---|
| at-most-once | авто-коммит офсета | задание может быть потеряно |
| **at-least-once** | `enable.auto.commit=false`, коммит после публикации | задание обработано повторно → дубль результата |
| exactly-once внутри Kafka | транзакция `send` + `sendOffsetsToTransaction` | дублей сообщений нет |

```python
p = Producer({"bootstrap.servers": BS, "enable.idempotence": True,
              "acks": "all", "retries": 2**31 - 1})
c = Consumer({"bootstrap.servers": BS, "group.id": "stt",
              "enable.auto.commit": False, "auto.offset.reset": "earliest"})

while True:
    msg = c.poll(1.0)
    if msg is None or msg.error():
        continue
    job = json.loads(msg.value())
    try:
        result = transcribe(job["payload"]["audio_url"])      # долгая работа
        p.produce("stt.results.v1", key=job["session_id"],
                  value=json.dumps(result).encode())
        p.flush(10)            # дождались ack брокера
        c.commit(message=msg)  # и только теперь двигаем офсет
    except TransientProviderError as e:
        if job["attempt"] < 3:
            produce_retry(job, attempt=job["attempt"] + 1)
        else:
            produce_dlq(job, reason=str(e))
        c.commit(message=msg)
```

Детали:

- `enable.idempotence=true` — производитель не создаст дубль при собственных ретраях;
- `p.flush()` перед `commit`, иначе коммит обгонит фактическую публикацию;
- `max.poll.interval.ms` должен быть больше худшего времени обработки.

Вариант с транзакциями Kafka: работа выполняется **вне** транзакции, транзакция открывается
только на публикацию результата вместе с коммитом офсета. Требует
`isolation.level=read_committed` у всех читателей, стабильного `transactional.id` на
инстанс и не покрывает внешние side effects (вызов провайдера, запись в S3). Дубли работы
при этом остаются.

### 4.4 Что изменится при переходе

- Воркеры из HTTP-обработчиков превращаются в консьюмеров — меняется только входной слой.
- Появляются топики, DLQ, конфигурация групп и ключ партиции.
- **Контракты:** брокерные схемы перенесены в `docs/contracts/archive/` и после перехода
  снова понадобятся, но их придётся сверить с HTTP-обменом, который действует сейчас
  (`docs/contracts/`): за время MVP появились `events`, `domain_commands` и снапшот SSE.
- Ретраи и дедлайны частично переезжают в брокер и DLQ.
- Появляется возможность запускать несколько экземпляров обработки.

### 4.5 Выбор брокера

| | Kafka | Redpanda | NATS JetStream |
|---|---|---|---|
| Ops | KRaft + брокеры, тяжёлая настройка | один бинарь, Kafka API | один бинарь |
| Совместимость | эталон | API Kafka | свой протокол |
| Request/reply | руками | руками | из коробки |
| Экосистема | Connect, Debezium, Streams | частично (API совместим) | своя, меньше |
| Для нашего кейса | избыточно по инфраструктуре | **предпочтительно**: знакомый API без ops | дешевле по коду, но новый стек |

При переходе проверить на выбранной версии поддержку транзакций и `read_committed` — нужны
только если понадобится exactly-once.
